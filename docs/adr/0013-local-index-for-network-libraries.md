# macOS 网络盘媒体库使用本机索引缓存

恢复实际 NAS 批次时，SQLite 在 SMB 上未启用 WAL，提交反复等待文件锁。隔离测试证实，保留桌面读连接或读完后关闭连接，都不能可靠避免冲突。我们将 macOS 网络卷的可重建索引放在本机配置目录的 `library-index/<库身份>/library.db`；本地卷沿用库内索引。媒体、sidecar、NFO 与操作日志仍在媒体库中，条目写入口仍只有 `Library::reindex_dir`。

库身份由规范路径、挂载来源及目录 inode 派生，不使用每次挂载可能变化的设备编号。打开后的读写连接绑定具体缓存文件与库根身份，换库、离线或替换路径均不能悄悄重新绑定。首次打开通过 SQLite backup API 将旧索引的一致快照复制到本机临时文件，再排他发布；旧索引保留且之后不再写入。复制失败不发布空缓存，允许稍后重试。新旧客户端不共享索引更新，外部媒体变化仍由重建索引核对。

我们拒绝依靠增加等待时间或强制网络卷锁模式解决问题；前者会按批次规模放大等待，后者不能证明锁语义可靠。新增服务也不符合单进程范围。本机缓存需要独立管理生命周期，但可直接使用受支持的 WAL 并保留现有只读快照模型。初始化检查 WAL 实际返回值，不能把设置语句执行成功等同于 WAL 已启用。

恢复文件操作完成后，索引是独立可重试的收尾步骤：归并已知影片的图片子目录，保留未列入 items 的操作目标；数据库错误停止整批索引尝试，报告剩余数；取消在当前文件恢复/索引事务的安全边界生效，原 Partial 日志继续支持重试。进度事件仍以 jobId 和库根隔离。快照迁移及索引工作在阻塞池执行，不占用 UI 线程。

参考：[SQLite WAL](https://www.sqlite.org/wal.html)、[网络文件系统限制](https://sqlite.org/useovernet.html)。本决策只实现并验收 macOS 网络卷检测，其他平台不宣称具有相同迁移行为。
