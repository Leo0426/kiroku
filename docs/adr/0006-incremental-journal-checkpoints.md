# ADR-0006：整理日志的增量持久化

- 状态：接受
- 日期：2026-10-11
- 关联：ADR-0002、ADR-0005

## 问题与约束

大批次整理在每个操作的意图、提交和撤销边界序列化全部历史，累计写入 O(N²)。不能延迟每项落盘，不能缩减已有媒体摘要、所有权、回滚或库身份校验。磁盘仍是媒体唯一真相，日志仍负责恢复已授权的操作。

## 方案比较

1. 保留原完整快照：简单且旧客户端可直接读取，但累计序列化和写入随批次平方增长。
2. 分离增量文件和快照：能降低写入量，但增加跨文件发布顺序、引用、遗留文件和维护清理规则。
3. 同一日志文件内保存初始快照和增量记录，收尾再生成完整 JSON：只保留一个历史入口，恢复和维护仍通过 Journal::load；以一个内部存储模块隐藏帧格式与写入游标。

选择第三种方案。

## 决策

`journal-<id>.json` 在增量阶段由版本化 magic、初始 Journal 快照和有序变更组成。每条记录含长度、内容 SHA-256，以及长度和内容摘要的校验和。记录只包含新增操作、证明、影片记录、撤销索引、修订记录，当前 pending/status/version，或指定修订的 undone 变化。

初始快照先写临时文件，同步后原子替换并同步父目录。之后每个原有持久边界追加一条记录并同步文件；没有放宽 fsync 或聚合多个未完成项目。写入器检查库和日志文件身份及已知长度，拒绝替换、掉线和过期克隆。新式日志的完整损坏记录、非法序号/索引及长度校验失败均报错；未完整写出的最后一条记录不生效，返回完整前缀并标记 Partial。重新读取后才可去掉已确认未完成的尾部、追加恢复进度。

`Journal::save` 仍输出原对象 JSON，并以原子替换完成合并；正常批次收尾及完整撤销使用它。直接 execute/replace_files 或中断任务在 save 之前可保留增量文件，当前 Journal::load/inspect/list 都能读取。加载旧 v1–v4 对象和裸 Vec<Op> 后可以继续持久化和撤销；旧客户端不会把增量文件误解析成已完成的空日志。领域日志版本、操作和证明字段保持不变。

读写使用 64 KiB 缓冲，回放逐条处理，不再另读一份完整文件字节。完整 Journal 模型仍 O(N)，单条大快照或批量修订的领域数据亦不承诺固定空间。内部增量入口只处理核心自身的追加式变化；外部任意编辑仍用 save 的完整快照。

## 压力场景与代价

- 正常整理：意图同步后才准备/发布媒体，提交同步后才报告完成。
- 进程退出或尾部撕裂：此前完整意图仍可用；暂存/目标身份与摘要继续决定恢复和撤销，不能仅凭目标存在推断成功。
- 写入失败：后续项目停止，保留此前完整前缀与待恢复媒体；重新读取日志后可恢复。
- 库切换、掉线、文件被替换或旧克隆写入：身份/长度不匹配拒绝保存，不重建旧库。
- 旧日志：原 JSON 和裸数组仍可读取，首次继续执行/撤销只做一次格式转换；遗留的普通临时写入文件可安全复用，符号链接或目录不会被覆盖。
- 回滚：每项撤销继续独立同步记录，只有进度成功持久化后才清理所有权锚。
- 累计写入：初始快照、增量和最终合并合计 O(N)，仍有每边界同步的固定延迟。完整日志读取/模型、恢复时读取媒体 SHA，以及列表聚合成本没有消失。

代价是新增帧回放和存储游标。格式限制在 journal/storage.rs 内，不增加数据库、服务、后台自动任务或新的对外命令。

## 历史读取的资源边界

只读历史模型共享库根身份锚（弱引用登记最多 16 个），不保留每份日志的文件描述符。读取时随既有流计算整文件摘要和文件身份 token；首次保存/恢复时再次完整核对内容与身份，再绑定该活动写入器的文件句柄。不能只凭时间戳激活写入。活动写入之后每边界继续用强文件句柄和长度检查，不重复重读历史。独立进程加载 250 条历史的句柄增长测试防止回归。

## 修订：同一影片内合并边界（2026-10-15）

原决策「每个原有持久边界追加一条记录并同步文件；没有……聚合多个未完成项目」在单部影片内放宽为：

- 项目开始（Partial 状态、影片记录）不再单独同步，随该影片第一个操作的意图帧写入。
- 每个操作的提交只改内存，随同一影片下一个操作的意图帧写入；影片的最后一个提交在 `execute` 返回前同步，调用方仍在提交落盘后才报告该影片完成。
- 不跨影片聚合：每部影片结束时都会落盘。

为什么安全：意图帧仍在该操作任何媒体改动之前同步。提交延后时，崩溃后的日志里该操作仍是 pending，状态与原来「发布后、提交同步前崩溃」完全相同，由 `recover_pending` 按暂存文件身份和摘要补记或清理，没有新增恢复路径。一帧内的提交与下一意图是原子的，要么都在要么都不在。日志尚未写过（没有任何媒体改动）时结束不补写，避免在库掉线后重建库目录。

效果：每部 3 个操作的影片，日志同步从 7 次降到 4 次；release 下 200 部合成影片 apply 从 16.4 s 降到 12.3 s（约 82 → 61 ms/部）。测量记录在本地工作笔记中（不入库）。文件、暂存、发布目录和源目录的同步不变，也没有改用 `F_BARRIERFSYNC`。
